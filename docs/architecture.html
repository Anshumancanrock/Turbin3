A per-wallet SOL vault where custody rests on program-derived addresses rather than on any key a person holds — and where withdrawing also registers the caller with a second program, through a cross-program invocation.

FIG 1 What talks to what

Three programs and four accounts. The vault program owns the two accounts that hold a user's position; it never writes to lamports or to the registration record directly — it asks the programs that own them.

FIG 2 Where the addresses come from

None of these three accounts has a private key. Each address is derived by hashing a list of seeds together with a program ID until the result falls off the ed25519 curve — that off-curve byte is the bump. Because the derivation is deterministic, anyone can recompute an address; because it is off-curve, only the owning program can authorise it.

FIG 3 The lifecycle

Four instructions, run in order. The numbering is the actual sequence — deposit cannot run before initialize has created the state account, and close is terminal.

STEP 01initialize

Creates vault_state with the user as payer, then writes both bumps into it. Anchor finds the canonical bumps once here so that every later instruction can read them back instead of re-deriving — cheaper in compute, and it pins the addresses.

vault_state: created · vault: 0 lamports
STEP 02deposit

Invokes the System Program to move amount from the user to the vault. The lamports leave the user's own account, so the user's signature on the transaction is all the authority needed.

vault: + amount
STEP 03withdraw

Moves amount back out of the vault — this time the program signs as the PDA — and then registers the caller with the registration program. See Fig 4.

vault: − amount · application_account: created (once only)
STEP 04close

Drains whatever is left in the vault to the user, then closes vault_state and refunds its rent. The user can call initialize again afterwards; the registration record is untouched and cannot be recreated.

vault: 0 · vault_state: closed

FIG 4 Inside withdraw: two invocations, three programs

This is the extension. One transaction from the user fans out into a call tree; the bracketed numbers are invocation depth, exactly as they appear in the transaction log.

FIG 5 Who authorises each move

The one idea worth taking away. A PDA has no private key, so a program proves authority over it by handing the runtime the seeds that derive the address.
